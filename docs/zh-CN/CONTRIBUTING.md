# 为 12pit 贡献

参与翻译请看[翻译指南](https://github.com/12src/12pit/blob/main/docs/zh-CN/TRANSLATING.md)。

## 开始贡献

欢迎修复缺陷、完善文档、补充测试、维护项目或开发新功能。

选择带有 <https://github.com/12src/12pit/labels/confirmed> 和 <https://github.com/12src/12pit/labels/help%20wanted> 标签的未关闭议题。刚接触本项目的贡献者可以从带有 <https://github.com/12src/12pit/labels/confirmed> 和 <https://github.com/12src/12pit/labels/good%20first%20issue> 标签的议题开始。开始前，先查看负责人、评论和关联的拉取请求。

开发较大的功能，或改动需要讨论设计时，请先创建议题。[议题指南](https://github.com/12src/12pit/blob/main/docs/zh-CN/ISSUES.md)说明了需要提供的信息。改动范围还没确定时，可以在议题中或 [Discord](https://discord.gg/e9PRKMUenc) 的 `#developer` 频道讨论。

## 认领议题

开始处理议题时，请留条评论。如果你的工作可能与他人重叠，请先提交草稿拉取请求，方便大家了解进度。

## 开始工作

每个提交只做一项改动。推荐使用[约定式提交格式](https://www.conventionalcommits.org/)，例如 `fix: correct profile loading`、`docs: clarify build steps`。每个拉取请求通常围绕一个目标，便于一起审查的少量相关改动可以放在一起。

[架构指南](https://github.com/12src/12pit/blob/main/docs/zh-CN/ARCHITECTURE.md)介绍了各包的职责和依赖。[调试指南](https://github.com/12src/12pit/blob/main/docs/zh-CN/DEBUGGING.md)说明了如何运行开发客户端和执行检查。

先阅读相关代码，复用合适的辅助工具。新逻辑放在所属功能中，有实际需要时再提取共享代码。代码清理也应围绕当前改动。

[BootstrapLayoutTest](../../src/test/java/pit12/architecture/BootstrapLayoutTest.java) 会创建配置对象，检查配置分类。无需注入依赖的配置使用 public 无参构造器。新配置需要注入依赖时，请更新测试中创建它的方式。

项目中的说明文字都使用自然的短句，优先用常用词。项目术语能把意思说得更清楚时，就用项目术语。

## 编码规范

先满足功能当前的需要。有第二个实现或测试等实际需求时，再添加接口或包装器。

提取方法、常量或变量能提高可读性，或有多处使用时，再做提取。只用一次且内联写法清楚的内容，直接内联。合并作用相同的方法，省去只转发调用的包装方法。

在用户输入、文件和网络数据、可能缺失的 Minecraft 值进入项目时检查。内部调用由调用方保证数据有效。内部不变量被破坏时，按缺陷就地处理，让错误显现出来。`stop()` 可能在初始化失败后调用，要能处理尚未创建的资源。

将集合交给可能修改它的使用者，或传给其他线程时，才复制集合。

在客户端线程访问实时状态。文件读写、HTTP 请求和开销大的计算交给组件自己的工作线程。应用异步结果前，确认所属组件仍在运行，且请求或任务代次仍有效。任务依赖连接或世界时，也要检查对应的身份标识。

先完成状态更新，再通知监听器，让回调读取更新后的状态。

加载失败时保留原文件，写入失败时保留未保存的改动。检查保存修订号后，再将数据标记为已保存。修改文件格式时兼容旧版本，并保持已保存的 ID 稳定。

能处理异常或向调用者提供更多信息时，才捕获异常。删去只重新抛出或忽略异常的 `catch` 块。

避免明显的浪费，例如每帧解析或扫描整个世界。添加缓存或特殊处理前，先测量收益。收益很小、复杂度却很高时，优先用简单方案。

清理当前改动中未使用的方法、字段、参数、导入和类。删除公开成员前，先在整个仓库中搜索使用处，包括测试、文档和 Mixin 配置。

使用语言自带的写法。装箱交给语言自动处理，通过导入引用类型。

## 注释

从初次阅读者的角度看代码。用途、行为或契约容易被误读时，补一句简短注释。代码已经清楚表达的内容就交给代码。修改代码时，也要更新相关注释。

## 提交合并请求

使用 `./gradlew spotlessApply` 和 `npm run format --prefix web-ui` 格式化代码。提交拉取请求前，运行相关检查并构建一次，说明实际执行的检查和已知限制。行为有变化时，补充有针对性的测试。

说明改了什么、为什么改，并报告失败的检查。完成后，将草稿拉取请求标记为可供审查。
